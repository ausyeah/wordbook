# 单词书联网版 · 技术方案与实现分析

> 面向汇报与求职的项目技术文档。涵盖系统架构、核心设计决策、工程难点复盘、性能优化与演进规划。
> 代码仓库：https://github.com/ausyeah/wordbook （MIT + 数据署名，敏感信息已脱敏）

---

## 1. 项目概述

**一句话定位**：一个多设备云端同步的背单词 Web 应用——前端为零依赖原生 SPA，后端为腾讯云 CloudBase HTTP 云函数 + PostgreSQL，全栈可维护代码约 2000 行，基础设施成本趋近于零。

### 1.1 背景与定位演变

项目起源于一个本地 Python Tkinter 单机自测程序，经历了三次形态演进：

| 阶段 | 形态 | 关键问题 |
|---|---|---|
| v0 | 本地单机版（Python Tkinter） | 无同步、无移动端 |
| v1 | Cloudflare Workers 全栈 | 国内网络不可达（`workers.dev` 被阻断、POST 请求体被中间层吞掉） |
| v2（当前） | 腾讯云 CloudBase 全栈 | 稳定可用，持续迭代中 |

产品定位也在使用中完成了一次重要校准：从"给初学者的 SM-2 间隔重复工具"调整为"**面向有词汇基础用户的快速刷一轮 + 错题强化工具**"（详见 §4）。这个演变直接驱动了复习调度器的重写与一次存量数据迁移。

### 1.2 项目规模

| 指标 | 数值 |
|---|---|
| 手写代码量 | 约 2000 行（前端 SPA 1547 行 + 后端 440 行，不含词库数据与锁文件） |
| 词库 | 4356 词（907 KB JSON，静态下发） |
| 后端 API | 9 个 REST 端点 |
| 数据模型 | 4 张表，`word_state` 19 列 |
| 基础设施成本 | CloudBase 体验版，≈ ¥0/月 |
| 可用性 | 上线以来持续运行，双端（手机/PC）真实日常使用 |

## 2. 系统架构

```
┌─────────────────────────────┐      ┌──────────────────────────────┐
│  前端 SPA（静态网站托管）        │      │  CloudBase HTTP 云函数 api     │
│  原生 HTML/CSS/JS，零依赖       │─────▶│  Node.js 20 + Express         │
│  · 渲染 / 路由 / 离线 outbox     │ HTTPS│  · 认证（PBKDF2 + HMAC 会话）   │
│  · localStorage 持久化          │◀─────│  · 同步引擎（幂等 + LWW）        │
│  · 结构化释义渲染 / CSS 图表      │ JSON │  · SRS 调度 / 错题本 / 统计聚合   │
└─────────────────────────────┘      └──────────────┬───────────────┘
        静态资源：index.html/styles.css/app.js        │ PostgREST
                  /vocab.json（4356 词）              ▼
                                       ┌──────────────────────────────┐
                                       │  CloudBase PostgreSQL          │
                                       │  users / word_state(19列)      │
                                       │  review_log / settings         │
                                       └──────────────────────────────┘
```

**架构决策要点**：

- **前后端同仓同部署**：一次 `deploy.bat` 同时完成云函数更新与静态托管发布，单人文册维护成本最低。
- **词库不入库**：4356 词作为静态 JSON 由 CDN 下发，数据库只存学习状态（每用户 ≤ 数千行），把数据库压力和流量成本降到最低。
- **云函数 = Web Server**：Express 监听 9000 端口，由 `scf_bootstrap` 拉起，网关按路径透传（`PathTransmission=2`），保留了向自建服务器迁移的代码兼容性。

## 3. 核心设计一：多设备数据同步引擎

这是项目里工程含量最高的子系统，解决三个问题：**多端并发写冲突、离线期间的操作不丢失、弱网环境下的可靠传输**。

### 3.1 写操作建模：op 流水 + 幂等去重

客户端不直接写状态，而是生成**操作流水（op）**：

```json
{ "type": "answer", "word": "radiate", "rating": 5,
  "occurred_at": 1787983280892, "op_id": "dev_x7k2:1787983280892:k3fmq1" }
```

- `op_id = 设备ID + 时间戳 + 随机串`，客户端生成，数据库 `review_log` 以 `(user_id, op_id)` 为主键。
- 同步时后端先查 `reviewExists(op_id)`：已存在则跳过但**返回当前权威状态**。这保证了同一批操作重放任意次，结果都一致——**幂等性由数据库唯一约束兜底，而不是依赖客户端"记得自己发过什么"**。
- 设置类操作走 `settings` 表（键值 + `updated_at`），状态类操作走 `word_state`。

### 3.2 状态合并：LWW + 版本号

词条状态采用**最后写入胜（LWW）**合并策略，辅以单调递增的 `rev` 版本号：

- 后端收到 `state` op 时，仅当 `op.updated_at > 当前行的 updated_at` 才应用；
- 应用时 `rev = cur.rev + 1`，保留完整审计线索；
- 同步响应把被触碰的行（`touched`）回传给客户端，客户端按 `updated_at` 与本地状态择新合并。

**为什么不用 CRDT / 向量时钟**：这是单人使用的工具，同一单词被两台设备在同一毫秒内写走的概率趋近于零，LWW + 幂等已经 100% 满足正确性。把分布式协调的复杂度花在真实需求上，是这个项目最重要的工程取舍——面试中这也是最能体现判断力的一点：**知道什么时候不需要复杂方案**。

### 3.3 离线 outbox：弱网下的操作不丢

```
答题 → 生成本地状态（即时反馈）→ op 压入 outbox → localStorage 持久化
     → flush()：取前 10 条批量化 → 成功则从 outbox 移除并合并云端返回状态
```

- outbox 先落 `localStorage` 再尝试发送，页面崩溃/断网/杀进程都不丢；
- 触发时机：每次答题后、`online` 事件、页面重新可见、30 秒轮询；
- **防并发锁**：`_flushing` 标志避免密集答题时重叠发送；
- **失败快速重试**：失败后 10 秒即重试（不必等 30 秒轮询周期），状态栏实时显示"已缓存 N 条"。

### 3.4 弱网传输适配：一次真实的网络层对抗

v1 部署在 Cloudflare Workers 时发现：GET 请求可达，但 **POST 请求体会被国内部分网络中间层静默丢弃**，表现为"注册时服务端从未收到 body"。解决方案是把全部写操作**GET 化**：

- 请求体序列化为 URL 查询参数（`/api/sync?ops=<URL编码的JSON>`）；
- 为控制 URL 长度，outbox 按 **10 条/批**分块（实测单批 URL ≈ 2KB，远低于中间层阈值）；
- 答题类 op 精简字段，单条 ≈ 120 字节。

迁移后国内全链路稳定。代价是 URL 编码开销与"GET 语义下不应有副作用"的 REST 纯度妥协——在可用性面前选择了 pragmatism，并在代码注释中记录了原因。

### 3.5 同步健壮性演进（问题 → 措施 → 效果）

| 问题 | 措施 | 效果 |
|---|---|---|
| 密集答题时多个 flush 并发重叠 | `_flushing` 互斥标志 | 消除重复请求 |
| 失败后固定 30s 才重试，体感"一直失败" | 失败后 10s 快速重试 + 成功即停 | 恢复时间 30s → ≤10s |
| 单批 15 条 URL 过长被网关拒绝 | 批次降至 10 条 | 消除 4xx |
| token 过期被误判为业务错误导致登出 | 401 白名单：login/register/reset 的 401 透传给业务层 | 错误提示准确 |

## 4. 核心设计二：复习调度器的产品化演进

### 4.1 起点：标准 SM-2

初版实现了教科书式 SM-2：答对间隔 1 → 6 → ×ease 天，`ease` 按 (5-rating) 调整，下限 1.3；答错重置间隔、降等级。前后端各持一份**镜像实现**（前端负责即时反馈，后端为权威计算），发布时必须保证两侧公式逐字符一致，否则同步时状态会来回翻转。

### 4.2 问题：真实使用暴露的定位偏差

上线后用户（目标用户即作者本人）两天内刷了约 500 词，SM-2 的"首次答对次日复习"把全部新学词堆到了同一天——**待复习 498 题**。根因不是 bug，而是 SM-2 的产品假设（初学者需要高频短期复习）与真实场景（有词汇基础、目标是快速把 4356 词过筛一遍）不匹配。

### 4.3 决策：从 SM-2 到"刷一轮 + 错题强化"

产品规则重新定义为：

| 行为 | 结果 |
|---|---|
| 答对 | `level=3`（掌握），`due_at = now + 365 天`，**本轮退出轮换** |
| 答错 | 进入错题本，`due_at = 次日 0 点`（东八区），连对 3 次毕业出本 |

配套的**存量数据迁移**用了一条幂等 SQL（经 ExecutePGSql 执行）：

```sql
UPDATE word_state
SET due_at = GREATEST(due_at, updated_at + 31536000000)
WHERE is_wrong_book = FALSE AND deleted_at = 0;
```

`GREATEST` 保证已标记远期的熟词不受影响，迁移可重复执行。**实测：523 条到期积压 → 迁移后仅剩 2 条**（均为错题本到期词），复习队列从此只服务于"错题强化"这一件事。

### 4.4 演进中的工程要点

- **前后端镜像一致性**：调度公式同时存在于 `app.js` 与 `api/index.js`，任何调整必须双侧同步修改，否则同步时 `updated_at` 较新的一方会用旧公式覆盖新结果。这是双端镜像架构的固有代价，也是文档里明确记录的维护约束。
- **等级语义重定义**：答对即 `level=3` 后，"掌握"统计的含义从"SM-2 三次复习通过"变为"本轮刷对过"，与快速刷一轮的产品语义一致；错题本内的词仍按既有规则封顶 `level=2`，毕业才可到 3，保留了"错过必须巩固"的约束。

## 5. 核心设计三：认证与安全

### 5.1 认证方案

- **密码存储**：PBKDF2-HMAC-SHA256，**100,000 次迭代**，16 字节随机盐，服务端只存 `salt:hash`；
- **会话**：自实现 HMAC-SHA256 签名令牌（`base64url(payload).base64url(hmac)`），30 天有效期，无状态校验，不需要会话存储；
- **找回密码**：恢复码机制（不存数据库，校验码部署时配置），避免引入邮件服务的复杂度；
- **多用户**：从"首用户锁定"演进为开放注册，唯一性由数据库 UNIQUE 约束保证，重复注册返回 409。

### 5.2 密码错误与令牌过期的错误语义分离

一个典型 bug：所有 401 都触发前端强制登出，导致"密码错误"也被包装成"登录已失效"。修复方案是 **401 白名单**——`login/register/reset-password` 三个公开接口的 401 是业务错误，透传给页面展示；仅受保护接口的 401 才代表令牌失效。这个小案例说明错误码的**语义分层**比错误码本身更重要。

### 5.3 开源脱敏管线

开源前执行了系统化的脱敏流程，并用脚本固化为可重复执行的管线：

1. **物理隔离**：部署凭据（腾讯云密钥）存放于 `tcb/.config/`，被 `.gitignore` 排除在仓库之外；
2. **占位符替换**：环境 ID、API 网关域名、JWT 密钥、恢复码共 4 类占位符，代码内置的兜底密钥改为 `please-set-...` 显式占位；
3. **特征扫描**：对成品仓库扫描 13 类敏感特征（密钥原文、环境 ID、AppID、账号手机号、旧域名、函数 ID 等），当前 0 命中；
4. **发布门禁**：`.gitignore` 排除 `.config/`、日志、缓存等 9 类文件。

## 6. 前端工程

### 6.1 零依赖、零构建的取舍

整个前端不使用框架与构建工具，直接静态托管。收益：首屏无水合、无 bundle 时代际差异、部署即发布、CDN 缓存友好；代价：需要自己管理组件边界与状态（以模块化函数 + 单一 `S` 状态对象组织，54 个函数按视图分组）。对工具类单页应用，这个决策的维护成本被证明可控。

### 6.2 结构化释义渲染

红宝书释义格式为 `"vt. vi. 散发，流露；发出 (光、辐射等) vi. 呈辐射状发散"`，四选一选项直接展示会是一坨挤在一起的长文本。实现了一个小型解析器：

- 正则识别词性标签（含 `vt./vi.` 复合标签、`modal.`/`usage.` 特殊标签），渲染为蓝色词性徽标；
- 按 `；` 拆分主释义与次释义，次释义缩进灰字呈现；
- 全程 `createElement` + `textContent` 构建，杜绝 HTML 注入。

### 6.3 纯 CSS/SVG 统计图表

不引入图表库，四类图全部手写：堆叠柱状图（flex 纵向堆叠 + 按比例 `flex` 分配）、横向正确率条、迷你柱图、SVG 环形图（`stroke-dasharray` 圆环 + 中心百分比）。打包体积增量为 0，移动端渲染无压力。

### 6.4 排版与缓存治理

- 中文字体栈 `仿宋 → Songti SC → Noto Serif SC`（iOS 无仿宋自动回退宋体），西文 Georgia，形成纸面阅读感；
- 静态资源带版本参数（`app.js?v=yyyymmddX`），每次发布递增，解决"CDN + 浏览器双重缓存导致改版不生效"的问题——这是国内静态托管环境下反复踩坑后的标准解法。

## 7. 工程化与部署

- **一键部署**：`deploy.bat` 封装 CLI 安装（首次自动装入用户目录，不污染项目）、占位符未替换检查、云函数 + 静态托管两段部署与一致性校验；
- **凭据隔离**：CLI 凭据通过 `USERPROFILE` 重定向固定在项目私有目录，与开源目录物理隔离；
- **发布校验**：托管发布启用 `--verify`（远端文件一致性校验）+ 版本参数递增，双保险对抗缓存。

## 8. 问题实录（精选踩坑）

| # | 现象 | 根因 | 解法 |
|---|---|---|---|
| 1 | 注册请求服务端收不到 body | 国内网络中间层丢弃跨境 POST body | 全部写操作 GET 化 + 参数分批 |
| 2 | 线上更新后用户手机仍是旧版 | 静态托管 CDN 边缘 + 浏览器磁盘缓存双层缓存 | 资源版本参数 + 无痕窗口验证流程 |
| 3 | 输错密码被强制登出 | 401 语义未分层 | 401 白名单透传业务错误 |
| 4 | 待复习积压 498 题 | SM-2 产品假设与目标用户不匹配 | 调度器重写（§4）+ GREATEST 幂等迁移 |
| 5 | 通过 `.cmd` 垫片执行 SQL 时报"找不到文件" | 垫片经 cmd 二次解析，SQL 中 `<=` 被当作输入重定向 | 改写为 `BETWEEN` / `GREATEST` 规避尖括号 |
| 6 | 401 全部触发登出 | 错误语义未分层 | 同 #3，白名单方案 |

> #5 值得展开：任何"命令 A 包裹命令 B"的调用链（shell → cmd 垫片 → node），特殊字符都会被多层解析器各解释一次。定位方法是二分注入点：先确认参数到达了哪一层，再逐层对齐转义规则。

## 9. 性能与优化汇总

- **传输**：同步批处理 10 条/批；词库 907KB 走 CDN 静态下发（带 `cache: no-cache` 协商与 3 次自动重试、20s 超时、失败兜底页）；
- **数据库**：词库不入库；`(user_id, word)` 主键点查 + `(user_id, due_at)` 索引服务复习队列；分页拉取全量状态（100 行/页）；
- **渲染**：词库列表先排序后截断 500 条（避免"排序前截断"导致最新学习的词被挤出）；选项行高自动对齐、徽章统一顶对齐；
- **可靠性**：答题数据三级兜底（内存状态 → localStorage outbox → 云端），任一环节失败均可恢复。

## 10. 反思与演进规划

**做得好的**：同步引擎的正确性设计（幂等 + LWW + outbox）经受住了双端日常使用验证；产品定位校准驱动调度器重写，展示了"算法服务于场景"的取舍能力；开源脱敏管线化，可重复执行。

**自知不足**：无自动化测试与 CI（同步引擎的幂等/LWW 逻辑目前靠手工全链路验证，是最该补测试的地方）；前后端 SRS 镜像存在漂移风险；可观测性只有客户端状态栏，缺少结构化日志与指标。

**演进方向（AI 应用层）**：

1. **AI 词卡**：LLM 流式生成词根拆解/记忆法/例句，生成结果落库（同词不重复生成的成本控制）；
2. **语义缓存**：pgvector（现有 PostgreSQL 直接扩展）做 embedding 相似度缓存，量化调用成本下降；
3. **LLM 网关**：多模型路由、限流配额、token 计量、降级熔断——把项目的 AI 调用收口到自建网关层；
4. **Eval 回归**：对 AI 生成内容做规则 + LLM-as-judge 自动评测，prompt 改动可回归。

这四项与现有架构零冲突：网关落在云函数层，向量能力落在 PostgreSQL，评测落在 CI。
